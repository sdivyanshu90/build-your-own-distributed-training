# Benchmarks

> **Everything in this file except the last section is measured on CPU with the gloo
> backend, on a shared laptop-class machine. These are not GPU numbers and must not be
> read as GPU performance.** The harness validates scaling of the *work*, software
> overhead, memory partitioning, checkpoint cost and recovery behaviour; it cannot
> predict tokens/s or MFU on GPUs/NCCL. No GPU number is extrapolated anywhere.

## Hardware and software

| Item | Value |
|---|---|
| Machine | WSL2 on Windows, kernel 6.18.40.1-microsoft-standard-WSL2 |
| CPU | 11th Gen Intel Core i5-1135G7 @ 2.40 GHz, 8 logical CPUs |
| RAM | ~5.8 GB visible to WSL2, **shared with other jobs and the desktop** |
| Python / torch | 3.10.12 / 2.6.0+cpu (inside the repo's `torch>=2.3,<2.7` pin) |
| Backend | gloo (TCP over loopback); no CUDA devices used (`CUDA_VISIBLE_DEVICES=""`) |
| Date | 2026-10-04/05 |
| Raw data | `benchmarks/results/*.jsonl` (each record embeds platform, CPU, torch, thread counts and the 1-minute load average at the end of the run when recorded) |

**The machine was not quiet.** Other agents' jobs (builds, tests, an LLM server)
shared the 8 logical CPUs and the RAM throughout; the 1-minute load average was
typically 5-25 during the measurements. All timings therefore carry substantial noise
(see "Limitations"); only large effects (2×+) are interpreted.

## Methodology

* **Driver**: `benchmarks/run_all.sh <stage>`; one `torchrun --standalone` per
  data point, each wrapped in `timeout` and guarded by a free-RAM check (≥ 1.5 GB
  available); at most 4 ranks.
* **Threads**: `OMP_NUM_THREADS=MKL_NUM_THREADS=1` per rank, so `world_size × threads
  ≤ 4`. (A second "total budget of ~6 threads" policy was planned but dropped for time;
  with one thread per rank, parallel efficiency isolates communication/overhead rather
  than cache or thread effects.)
* **Workload**: the real `Trainer` + `train_step` (`benchmarks/bench_train.py`), `test_tiny`
  config with model overrides (`benchmarks/_common.py::MODEL_PRESETS`): `tiny` 90,432,
  `small` 4,000,000, `mid` 27,795,968 parameters; fp32 everywhere; synthetic data.
  Throughput: `small`, micro-batch 4, seq 128, `grad_accum_steps=2` (from the YAML), 3
  warm-up + 20 timed steps. Reported tokens/s = global tokens per step × steps ÷ wall
  time over the timed steps; the median step time is also listed.
* **Weak vs strong scaling**: DP/FSDP runs keep the per-rank micro-batch fixed (global
  batch grows with `dp`, weak scaling); TP runs keep the global batch fixed (strong).
  "Efficiency" = speed-up over the 1-rank run ÷ number of ranks.
* **Memory**: per rank, (a) peak RSS (`ru_maxrss`, includes the ~0.3 GB torch runtime
  and, with FSDP, the transient full model built before sharding) and (b) the bytes
  of parameters, gradients and optimizer state actually resident on that rank at the
  end of the run (`state_bytes`), which isolates the sharding effect from the runtime.
* **Collectives**: `benchmarks/bench_comm.py` (fp32 buffers, 5 warm-up + 30 timed
  iterations, median/p90, algbw/busbw as in nccl-tests) and
  `benchmarks/count_collectives.py` (profiler op counts for one `train_step`).
* **Resume / checkpoint**: `benchmarks/bench_resume.py` (continuous run vs save at half
  and resume in a fresh `Trainer`, per-step loss comparison).
* **Fault**: `benchmarks/bench_fault.py` (real SIGKILL of one worker).
* **Convergence**: 150 steps of `tiny`, global batch 16 sequences in every layout.

## Why the 125M and 7B configs were not run

`config/125m.yaml` has 151.9M parameters: fp32 weights + gradients + two Adam moments
are `16 B × 151.9M ≈ 2.4 GB` for one replica, and FSDP builds the full model on every
rank before sharding (4 ranks × 0.6 GB transient, plus ~0.3 GB runtime per process).
With ~5.8 GB total RAM shared with other jobs this clearly exceeds the ~3 GB budget, so
it was not attempted. 7B (6.7B parameters, needs TP=8 and GPUs) is out of reach by
three orders of magnitude. The `mid` preset (27.8M) is the largest model measured.

## Results

All tables below are generated by `benchmarks/make_report.py` from `benchmarks/results/*.jsonl`
(full text in `benchmarks/results/SUMMARY.md`). **Data points that did not complete (timeouts on the shared machine) and are therefore absent, not estimated:** 2D FSDPxTP throughput (`2d_dp2tp2_pr`); memory run `mem_zero2_dp2`; memory run `mem_fsdp_dp2`; memory run `mem_fsdp_dp4`; memory run `mem_tp2`; memory run `mem_2d_dp2tp2`; convergence run `conv_tp2`; convergence run `conv_2d`; resume benchmark at world size 2 (FSDP dp=2); collective bandwidth at world size 4.

### Throughput and scaling (`small` model, 1 thread per rank, CPU/gloo)

| run | layout | world | dp | tp | threads/rank | tokens/step | median step (ms) | tokens/s | vs 1 rank | efficiency |
|---|---|---|---|---|---|---|---|---|---|---|
| dp1_pr | single | 1 | 1 | 1 | 1 | 1024 | 601 | 1536 | 1.00x | 100% |
| dp2_pr | FSDP | 2 | 2 | 1 | 1 | 2048 | 972 | 1884 | 1.23x | 61% |
| dp4_pr | FSDP | 4 | 4 | 1 | 1 | 4096 | 2616 | 1320 | 0.86x | 21% |
| tp2_pr | TP | 2 | 1 | 2 | 1 | 1024 | 1192 | 778 | 0.51x | 25% |
| tp4_pr | TP | 4 | 1 | 4 | 1 | 1024 | 1623 | 519 | 0.34x | 8% |

Reading: with 1 thread per rank on a shared machine, FSDP at 2 ranks gives the only
speed-up (1.2x tokens/s for 2x the cores); 4 ranks is *slower than one process*, and TP
is slower than one process at 2 and 4 ranks. This is the expected outcome of putting
a 4M-parameter model (about 0.6 s of single-thread compute per step) on a
loopback-TCP collective backend: every FSDP unit gathers and every TP sub-layer
all-reduces (collective counts below) while the collective latency floor is about 0.6-1 ms
(table below) and the ranks compete for the same cores with each other and with other
jobs. Candidate explanations beyond that (DTensor dispatch overhead on CPU, redundantly
replicated embedding/LM-head/logits work under TP) are hypotheses; they were not
isolated. The run-to-run noise is large (load average 5-25 during the runs), so only
the qualitative picture - parallelism does not pay on this hardware at this model size -
should be taken from the table, not the exact percentages.

### Fault recovery (SIGKILL one of 2 ranks)

| world | save every | step at kill | committed ckpts | resumed from | steps lost | detect (s) | relaunch->first step (s) |
|---|---|---|---|---|---|---|---|
| 2 | 10 | 25 | step_10,step_20 | 20 | 5 | 5.61 | 62.28 |

`detect` = SIGKILL to `torchrun` exiting (its agent tears down the survivors; no
collective timeout was involved). `relaunch->first step` = relaunch of the whole job with
`--resume-from <run dir>` to the first post-resume metric line, which includes Python/torch
start-up, process-group init, model build, checkpoint load and the data replay, on a loaded
machine. The last checkpoint was step 20 and the job had reached step 25: 5 steps of work lost.

## Limitations (read before quoting a number)

* CPU/gloo only; gloo runs collectives over TCP loopback with CPU cores doing both
  compute and communication, so "communication is cheap/expensive" statements do not
  transfer to GPUs with NVLink/NCCL.
* Shared machine: noisy timings; single run per data point (no repetition across
  sessions); medians over 20 steps within a run only.
* One thread per rank, ≤ 4 ranks, tiny/small/mid models; small models make every
  collective latency-bound.
* RSS includes allocator caching and the torch runtime; compare *resident state bytes*
  for the sharding effect.
* The MFU numbers in logs are meaningless on CPU.

## What to expect on GPUs (qualitative, not measured here)

* FSDP all-gather/reduce-scatter overlap with compute on separate CUDA streams
  (`forward_prefetch`, `BACKWARD_PRE`), so FSDP's overhead is usually far smaller than
  the gloo numbers above suggest as long as per-layer compute ≥ per-layer gather time;
  small models and slow links (PCIe, inter-node) re-expose it.
* TP all-reduces are on the critical path every layer; they are cheap over NVLink and
  expensive over PCIe/Ethernet, which is why TP should stay inside a node.
* Memory partitioning (the per-rank resident state) follows the formulas in
  PARALLELISM.md exactly regardless of backend; activation memory and the replicated
  logits dominate once the state is sharded.
* bf16 halves gather traffic (`param_dtype`), fp32 `reduce_dtype` keeps reduction
  traffic at 4 B/element; the optimizer step is memory-bound on GPU.
* The structural results here — equivalence to the single-process reference, collective
  counts, resume bit-exactness, recovery procedure — are expected to carry over; the
  magnitudes (tokens/s, scaling efficiency, latency) are not.

## Single-GPU (MX330) validation: NOT performed

The owner asked for a world-size-1 CUDA validation on the local NVIDIA GeForce MX330
(2 GB, Pascal sm_61) behind a mandatory thermal guard (start only below 80 °C, abort at
90 °C). **No GPU run was made, so there are no GPU results in this repository.**

* A `cu126` build (`torch==2.6.0`, `--index-url .../whl/cu126`, matching the repo's
  `<2.7` pin) was installed in `/tmp/claude-1000/flagship-dt/venv-cuda` (outside the
  repo), but the `torch.cuda.is_available()` / matmul+backward check never executed:
  the GPU lock was held by another job for the whole session.
* The thermal precondition was never met: `nvidia-smi` sampled once a minute from
  00:22 to 02:11 (99 samples, GPU idle from this project's side) reported
  **82-86 °C** with SM clock 139 MHz and `clocks_throttle_reasons.active = 0x20`
  (software thermal slowdown) throughout, i.e. above the 80 °C start threshold, so
  the guard rule required skipping.
* Consequently these remain **unverified on GPU**: the NCCL path (process-group init,
  device placement), FSDP on CUDA, checkpoint save/load from CUDA (including the FSDP
  re-keyed optimizer-state path), the fp16/bf16 behaviour on Pascal (the MX330 has no
  bf16 hardware; the repo defaults to `bfloat16` params, so a Pascal run needs
  `param_dtype: float16`/`float32`, and there is **no `GradScaler`** in the code, which
  fp16 would need), and the skipped CUDA test stub. Treat the mixed-precision paths as
  untested. The MX330 is a low-end mobile GPU in any case; it could only validate
  correctness of the single-device path, not multi-GPU behaviour.
